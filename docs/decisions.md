# Decisions

Журнал архитектурных решений. По философии проекта у каждого решения есть цель, альтернативы и причина выбора.

## D1. Фронтенд-стек M1

**Цель.** M1 работает целиком в браузере, без бэкенда и LLM. Нужен стек, в котором канвас и документ читают и пишут одну модель данных, а агент уверенно строит его автономно.

| Что | Выбор | Альтернативы | Почему |
|---|---|---|---|
| Основа | React + TypeScript + Vite | Vue, Svelte, Next.js | Самый распространённый стек, агент в нём сильнее всего. Типы ловят ошибки синхронизации. Next.js не нужен без бэкенда. |
| Вайтборд | `@excalidraw/excalidraw` как React-компонент | iframe на excalidraw.com, tldraw | Из iframe нельзя надёжно забрать данные. Компонент отдаёт сцену в наше хранилище и умеет `exportToSvg` для миниатюр и картинок в документе. Excalidraw выбран автором как лучший вайтборд. |
| Rich text | TipTap | Lexical, Slate, textarea + Markdown | Одинаковый редактор в Component Editor и в документе. Структурированный контент легко превратить в Markdown. |
| Состояние | Zustand | Redux Toolkit, React Context | Одно хранилище на оба режима, минимум шаблонного кода. |
| Хранилище | IndexedDB | `localStorage` | Сцены Excalidraw тяжёлые, лимита `localStorage` (~5 МБ) может не хватить. |
| Стили | Tailwind | CSS Modules, component library | Быстро повторить мокапы. |
| Экспорт MD | Генерация из модели | Конвертация HTML → MD | Модель — источник правды, вывод детерминирован и тестируем. |
| Экспорт PDF | Печать браузера с print-стилями | `pdfmake`, `jsPDF`, серверный рендер | Без тяжёлых зависимостей, текст выделяемый. Минус: системный диалог печати вместо файла в один клик. |
| Тесты | Vitest + Playwright | Jest, Cypress | Vitest нативен для Vite. Playwright даёт e2e и скриншоты для визуальной проверки агентом. |
| Пакеты | pnpm, Node `>=22` (`engines`) | npm, yarn | Быстро, строгие зависимости. Локально Node 25, Vercel собирает на своём LTS. |
| Деплой | Статическая сборка на Vercel | GitHub Pages, Netlify | Выбор автора. |

## D2. Библиотеки для раскладки канваса и ZIP-экспорта

**Цель.** Карточки канваса перетаскиваются и меняют размер, раскладка сохраняется и сбрасывается к исходной. Markdown-экспорт с диаграммами скачивается одним архивом.

| Что | Выбор | Альтернативы | Почему |
|---|---|---|---|
| Сетка канваса | `react-grid-layout` | `dnd-kit` + своя логика ресайза, CSS grid без перетаскивания | Перетаскивание, ресайз и сериализуемая раскладка из коробки. Раскладка — простой JSON, её легко хранить в модели и сбрасывать. |
| ZIP | `JSZip` | `fflate`, `client-zip` | Самая известная, стабильный API, агент уверенно с ней работает. Размер для десятка SVG не важен. |

## D3. TypeScript 6.0, а не 7

**Цель.** `pnpm lint` (typescript-eslint) и `pnpm typecheck` работают на одной версии TypeScript.

| Выбор | Альтернативы | Почему |
|---|---|---|
| `typescript@~6.0` | TS 7 (нативный компилятор) + отдельный линтер без типов; TS 7 для typecheck и TS 6 для линтера | TS 7 не отдаёт JS API, typescript-eslint 8 с ним падает и поддерживает `<6.1`. Одна версия проще двух. Переход на 7, когда typescript-eslint его поддержит. |

## D4. IndexedDB без обёртки

**Цель.** Сохранять один дизайн в IndexedDB.

| Выбор | Альтернативы | Почему |
|---|---|---|
| Нативный IndexedDB API, ~30 строк в `src/store/persist.ts` | `idb`, `idb-keyval`, `localforage` | Нужны только `get` и `put` одной записи. Зависимость не окупается. |

## D5. Текст PDF в e2e-тестах: `pdfjs-dist` (dev)

**Цель.** AT-14 и export-04 проверяют, какой текст попал в PDF из `page.pdf()`.

| Выбор | Альтернативы | Почему |
|---|---|---|
| `pdfjs-dist` только в devDependencies | `pdf-parse`; распаковать потоки PDF через `zlib` и искать строки | Chrome пишет текст глифами подмножества шрифта, простым поиском по байтам его не найти. pdf.js — эталонный парсер от Mozilla, `pdf-parse` — обёртка над его старой версией. В сборку приложения не попадает. |

## D6. Подтверждения через `window.confirm` (заменено: свой `<dialog>`, см. `src/dialogs.ts` и дизайн-систему)

**Цель.** «Load example» и предупреждение о пустых секциях перед экспортом дают выбор «продолжить / отменить».

| Выбор | Альтернативы | Почему |
|---|---|---|
| Нативный `window.confirm` | Свой модальный диалог | Две кнопки и текст — ровно то, что умеет нативный диалог. Не нужен код фокуса, Escape и доступности. Минус: внешний вид браузера, а не приложения. Заменить на свой диалог, если понадобится оформление. |

## D7. «Только десктоп» через CSS media query (заменено: адаптивная вёрстка, D34)

**Цель.** Ниже 1280px показывать «Open on desktop», но печать (PDF) должна рендерить документ, хотя ширина бумаги меньше 1280px.

| Выбор | Альтернативы | Почему |
|---|---|---|
| Tailwind `max-xl:` + `print:` на двух контейнерах | `matchMedia` в React | JS-вариант размонтирует приложение при печати: страница печатается как заглушка. CSS решает это без кода. |

## D8. Подсказка значка Trade-offs: CSS-тултип

**Цель.** Значок весов (m11-02) — статус, а не кнопка; подсказка видна при наведении и при фокусе с клавиатуры.

| Выбор | Альтернативы | Почему |
|---|---|---|
| `<span role="tooltip">` внутри значка, показ через `group-hover` / `group-focus-visible`, значок с `tabIndex=0` и `aria-describedby` | Нативный `title`; библиотека тултипов (Floating UI, Radix) | `title` не показывается при фокусе с клавиатуры, появляется с задержкой и не проверяется тестом. Библиотека — новая зависимость ради одной подсказки. Цена CSS-варианта: карточка без `overflow-hidden` и поднимается по `z-index` при наведении, чтобы подсказку не перекрывали соседи. |

## D9. Высота карточки по содержимому: замер + раскладка рядами

**Цель.** m11-04: высоту карточки задаёт содержимое, пользователь меняет только ширину и порядок; ряды и порядок чтения как на мокапе.

| Выбор | Альтернативы | Почему |
|---|---|---|
| Карточка меряет свою естественную высоту (`ResizeObserver`), канвас переводит пиксели в строки сетки (`rowHeight` 4px, шаг 20px) и подставляет `h`. Свой компактор `flow` (`src/canvas/flow.ts`): карточки идут рядами слева направо, перенос, если не влезает; ряд начинается под самой высокой карточкой предыдущего | Вертикальный компактор react-grid-layout («кирпичная кладка»); встроенный `wrapCompactor`; уйти от react-grid-layout на CSS flex-wrap + свой drag | Вертикальный компактор при разной высоте сдвигает ряды вразнобой: Data & Features оказывается выше Validation, порядок чтения ломается. `wrapCompactor` считает все карточки высотой в одну строку и накладывает их. Уход с react-grid-layout — переписать drag и resize, а он зафиксирован в D-решениях. Шаг 20px даёт запас внизу карточки меньше 20px, в пределах 32px из AT-19. `allowOverlap: true`, чтобы при перетаскивании библиотека не расталкивала карточки: положение решает только `flow`. Сохранённое `h` — лишь первая оценка до замера. |

## D10. Меню шапки (Share, AI Review, «⋯»): нативный Popover API

**Цель.** m11-06/m11-07: всплывающие меню закрываются по клику снаружи и по Escape.

| Выбор | Альтернативы | Почему |
|---|---|---|
| Атрибуты `popover` / `popoverTarget` (`src/canvas/Menu.tsx`); пункты закрывают меню через `popoverTargetAction="hide"`; позиция под кнопкой задаётся в `onBeforeToggle` | Свой `useState` + слушатели `mousedown` и `keydown`; Headless UI / Radix Popover | Браузер сам даёт закрытие снаружи и по Escape и верхний слой без `z-index`. Поддержка: Chrome 114+, Safari 17+, это покрывает десктопную аудиторию M1. Библиотека — новая зависимость ради трёх меню. CSS anchor positioning не везде есть, поэтому позиция считается в JS одной строкой. |

## D11. Ряд карточек — по самой высокой

**Цель.** Владелец после M1.1: карточки одного ряда одинаковой высоты, так удобнее читать канвас.

| Выбор | Альтернативы | Почему |
|---|---|---|
| `flow` (D9) после раскладки ряда растягивает `h` всех его карточек до максимума в ряду | Каждая карточка своей высоты (как было в D9); CSS grid с `align-items: stretch` вместо react-grid-layout | Одна строка логики в уже существующем компакторе. Карточка меряет высоту своего содержимого, а не растянутой рамки, поэтому растяжение не зацикливает замер. Уход с react-grid-layout противоречит D1/D2. |

## D12. Раскладка канваса по умолчанию: 3×3, ширины 4 / 3 / 5

**Цель.** Владелец: раскладка по умолчанию занимает место оптимально; что пользователь поменял сам (ширину, порядок), остаётся как он решил. Одна и та же раскладка при первом открытии, после Reset layout, Clear design и Load example.

| Вариант | За | Против |
|---|---|---|
| **Фиксированная раскладка по умолчанию: три ряда по три карточки, в каждом ряду 4 / 3 / 5 колонок, «схемные» секции (Validation, Target Solution, Integration) в широких колонках** — выбран владельцем | Колонки выровнены, предсказуемо, без лишнего кода: ширины просто данные в `INITIAL_LAYOUT` | Если схема появится в узкой карточке, расширять её руками |
| Ширина по наполнению (только ключи — 3, схема — 6) с добивкой рядов и закреплением ручной ширины | Сама подстраивается под наполнение | Опробовано: раскладка «плывёт» при каждой новой схеме, нужны флаг `pinned`, добивка рядов и заморозка на время жеста. Владелец выбрал простоту |
| Мерить естественную ширину содержимого | Точнее | Карточки прыгают при наборе |

- У «схемных» секций новый дизайн начинается со схемы по умолчанию: обычный текст «Diagram» на вайтборде. Подталкивает объяснить решение схемой; удалил текст — схемы нет. Для документа, экспорта и правила «секция пустая» нетронутая схема по умолчанию считается пустой (`diagramNonEmpty`), иначе пустой дизайн экспортировал бы картинки «Diagram». Альтернатива «обычная диаграмма без исключений» ломает 7 приёмочных сценариев.
- У карточек две ручки ресайза: правые колонки стоят у края, а react-grid-layout не даёт тянуть вправо карточку у края (`x + w ≤ cols` в `calcWH`).
- Клик по миниатюре открывает Details.

## D13. Дизайн-система

**Цель.** Все экраны M1 и M2 выглядят как одно приложение и как мокапы, а агент не угадывает цвета по PNG заново в каждой фиче.

| Вариант | За | Против |
|---|---|---|
| **Подмножество стандартной палитры Tailwind + рецепты классов в `docs/design-system.md` + grep-проверка** — выбран | Ноль зависимостей, M1 уже почти соответствует, агент читает из репо | Нарушение ловит grep, а не сборка |
| Семантические токены в `@theme` (`bg-surface`, `text-accent`) | Смена цвета в одном месте | Переписать ~90 классов M1, лишний слой при четырёх палитрах |
| Артефакт Design System на claude.ai | Удобно смотреть | Агент его не видит, вторая копия |
| Без дизайн-системы | Ноль работы | Разнобой между фичами |

- **Акцент indigo** (выбор автора): на канвас-мокапе Diagram индиго, в редакторе и документе фиолетовый. M1 переведён на indigo.
- **Серые slate**, не gray с мокапа: на глаз не отличить, а M1 уже на slate (74 места).
- **Ошибка red**, не rose: M1 уже на red.
- **Шрифт системный**, не Manrope с мокапа: без зависимости и загрузки, разница видна только в крупных заголовках.

## D14. Бэкенд M2

**Цель.** AI-проверке, аккаунтам и облачным дизайнам нужен сервер. Минимум своего серверного кода, фронтенд остаётся на Vercel.

| Вариант | За | Против |
|---|---|---|
| **Supabase** (auth, Postgres + RLS, edge functions, Vault) — выбран | Всё нужное в одном сервисе, доступ к данным описывается RLS, а не своим API | Привязка к платформе |
| Vercel Functions + отдельные Postgres и auth | Всё на Vercel | Две-три интеграции вместо одной |
| Свой сервис (FastAPI / Node) на Fly или Railway | Полный контроль | Больше всего кода и поддержки |
| BYOK прямо из браузера, без бэкенда | Ноль серверного кода | Ключ в браузере, аккаунтов и облака всё равно нет. Автор отверг как костыль |

Тесты без внешних сервисов: Supabase локально (CLI + Docker), тестовый логин в обход Google только в локальном окружении, мок LLM-клиента с записанными ответами, мок Google Drive.

Статус: предварительно, автор согласен на Supabase «пока».

## D15. Авторизация

**Цель.** Логин с минимумом кода и трения для Middle+ ML-инженеров.

| Вариант | За | Против |
|---|---|---|
| **Только Google** — выбран | Нет паролей, сброса, подтверждения email; Google-аккаунт есть почти у всех | Отваливаются те, кому корпоративная политика запрещает Google-логин. GitHub добавляется позже настройкой |
| Email + пароль | Универсально | Больше флоу и поддержки |
| Несколько провайдеров сразу | Шире охват | Не нужно на старте |

Доступ к Drive не запрашивается при логине: `drive.file` запрашивается при первом экспорте в Google Docs (incremental authorization), потому что широкий consent screen при первом входе отпугивает.

Гость работает без логина как в M1 (IndexedDB, экспорт). Облако и AI-проверка — только после логина. При логине локальный дизайн переносится в аккаунт.

## D16. Хранение ключа LLM (BYOK)

**Цель.** Пользователь платит за свои вызовы LLM, а его ключ не утекает ни в браузер, ни в логи.

| Вариант | За | Против |
|---|---|---|
| **Ключ зашифрован в Supabase Vault, расшифровывается только в edge function** — выбран | Ключ не возвращается клиенту, в базе только ссылка на секрет, RLS закрывает доступ | Нужна аккуратность с логами функции |
| Ключ в браузере, передаётся с каждым запросом | Ничего не храним | Живёт в `localStorage`, уязвим к XSS, ввод на каждом устройстве |
| Наш ключ + квоты | Нулевое трение | Платит автор, нужен биллинг |

Правила: клиент может записать ключ, но не прочитать; в UI видны только последние 4 символа, «Replace» и «Delete». Ключ проверяется при сохранении дешёвым запросом. Заголовки и тела запросов к LLM не логируются. Rate limit на пользователя в edge function. Лимиты расходов пользователь ставит у провайдера.

## D17. Экспорт в Google Docs

**Цель.** Документ дизайна открывается в Google Docs одним кликом.

| Вариант | За | Против |
|---|---|---|
| **HTML документа → Drive upload с конвертацией в Google Doc** — выбран | HTML уже рендерится, таблицы конвертирует Drive, без новых зависимостей | Не проверено, переживают ли конвертацию картинки из HTML (data URI) |
| `.docx` → Drive upload с конвертацией | Картинки встраиваются надёжно | Новая зависимость для генерации docx |
| Google Docs API `batchUpdate` | Полный контроль | Сотни запросов, таблицы вручную |

Токен получается в браузере через Google Identity Services с scope `drive.file` (non-sensitive, видит только созданные приложением файлы), бэкенд не участвует и токены не хранит. Диаграммы растеризуются в PNG: Google Docs не принимает SVG. Спайк 2026-10-02 подтвердил вариант: Drive API (`files.create`, `mimeType: application/vnd.google-apps.document`, тело `text/html`) сохраняет PNG как data URI (проверено до ~230 КБ, `width` соблюдается), PNG по https, заголовки (становятся оглавлением Google Docs), таблицы с фоном строк и цветом текста, жирный, курсив, списки. Теряются SVG data URI и, похоже, моноширинный шрифт. Рамки таблиц без явного стиля становятся чёрными — в экспорте задавать их явно. Импорт через интерфейс Drive («Open with → Google Docs») HTML не конвертирует, только API.

## D18. Без Training / Real-Work Mode

**Цель.** Одна среда для тренировки и реальной работы.

Альтернатива из PRD — два режима, различающиеся подсказками и скорингом. Отвергнута автором: разницы нет. AI-проверка всегда по кнопке, задачу можно взять из библиотеки или описать свою.

## D19. Скилл для AI-проверки

**Цель.** Проверка опирается на готовый фреймворк, а не на промпт, написанный с нуля, и выдаёт находки, которые привязываются к полям модели.

| Вариант | За | Против |
|---|---|---|
| **`ml-system-design-review` из [ML-SystemDesign/MLSystemDesign](https://github.com/ML-SystemDesign/MLSystemDesign/tree/main/skills) (MIT), один раз скопированный в `vendor/`, + наш слой вывода** — выбран | Рубрика и severity уже продуманы авторами фреймворка, на котором построены секции | Скилл рассчитан на агента с файлами и выдаёт отчёт, а не структурированные находки |
| Свой промпт с нуля | Полный контроль над форматом | Повторяем чужую работу хуже |

Как используем: `SKILL.md` и `references/` передаются модели как контекст (кэшируемый), режим «doc-only, stage: design doc» задан жёстко. Вывод — наша схема (structured output): находка = severity (Critical / Major / Minor, как в скилле), измерение рубрики, привязка к полю модели или к дизайну целиком, `title` (одна строка, до ~80 символов), `evidence` (что сказано в дизайне), `why` (почему это важно), `fix`. Четыре текстовых поля повторяют формат находки скилла `<dimension> - <evidence>. <why>. Fix: <action>.` и нужны интерфейсу: без короткого `title` списки и комментарии показывали бы обрезанный абзац (альтернатива — один текст, отвергнута по этой причине). Gradecard и вердикт в M2 не запрашиваются.

Отклонение от PRD (помощник не проектирует за инженера): «Fix» остаётся в чистом виде. Альтернатива — переформулировать его в вопрос — отложена, пока нет инфраструктуры под тренировки. **Цель.** Владелец попросил адаптивный дизайн: на 1280px шапка переносилась в несколько строк (липкая панель ревью при этом считала её высоту за `4rem`), миниатюра диаграммы сжимала значения на карточке до «T..», ниже 1280px приложение не открывалось вовсе. Шапка редактора — одна строка `h-16` от `lg`; ниже `lg` панель ревью — оверлей поверх канваса, а не липкая колонка, поэтому от высоты шапки ничего не зависит. Документ: три колонки (оглавление, лист, комментарии) от `xl`, ниже — один лист, комментарии списком под ним. Печать не затронута: `print:` классы как были.

**Плотность канваса (уточнение владельца):** все 9 карточек должны помещаться в окно. ## D35. Окружения и пайплайн деплоя

**Цель.** Вывести M2 в облако для публичных пользователей так, чтобы схема, функции и настройки входа не расходились между окружениями, а ошибка не попадала сразу в prod. Решение владельца (2026-10-02): prod + staging, GitHub Actions, публичный вход.

| Вариант | За | Против |
|---|---|---|
| **Два Supabase-проекта; GitHub Actions: ветка `staging` → staging, ветка `main` → prod после ручного approve; фронтенд — Git-интеграция Vercel (Preview ветки `staging` с постоянным адресом → staging, Production → prod)** — выбран | Миграции сначала проверяются на staging; prod меняется только с подтверждением; постоянный адрес preview ветки `staging` — один точный origin для Google и CORS; повторяемо, без ручных команд; агент по-прежнему не имеет облачного доступа | Два проекта и набор переменных в GitHub; фронтенд может выйти раньше approve, поэтому миграции только expand/contract |
| Один prod-проект | Проще | Preview-деплои и проверка миграций против боевой базы |
| Ручной `supabase db push` по чек-листу | Без CI | Человек забывает шаг; нет проверки после деплоя |
| Supabase Branching | Ветка базы на каждый PR | Платная функция; лишнее для одного разработчика |

Уточнение владельца (2026-10-02): пока только staging, `main` не трогаем; деплой staging из ветки `staging`, задания деплоя пропускаются, пока переменные проекта не заданы. Настройки входа живут в дашборде, а не в `config.toml` (локальный конфиг включает email-вход для тестовых пользователей, его `config push` в prod был бы опасен). Не-секретные значения — переменные репозитория с префиксом `STAGING_`/`PROD_`; в environments только пароль базы и approve (иначе `keepalive.yml` ждал бы подтверждения).

## D37. CSP и заголовки безопасности

**Цель.** Сессия Supabase хранится в `localStorage` (SPA без своего сервера), поэтому XSS = кража сессии. Ограничить, откуда грузятся скрипты и куда уходят запросы.

| Вариант | За | Против |
|---|---|---|
| **Строгая CSP в `vercel.json` (`script-src 'self' accounts.google.com`, `connect-src` только Supabase и Google, `frame-ancestors 'none'`), `nosniff`, `Referrer-Policy`, `Permissions-Policy`; `vite preview` отдаёт те же заголовки, e2e падают на любом нарушении** — выбран | Один источник заголовков для прода и тестов; нарушение ловится до деплоя; inline-скрипт из `index.html` вынесен в модуль, `unsafe-inline` для скриптов не нужен | `style-src 'unsafe-inline'` остаётся (Excalidraw и TipTap ставят inline-стили); новые внешние адреса нужно добавлять в CSP |
| Без CSP | Ноль работы | XSS без второй линии защиты |
| CSP через `<meta>` | Без настроек хостинга | Не поддерживает `frame-ancestors`; не проверяется на заголовках |

Excalidraw вписывает `esm.sh` последним запасным адресом в каждый шрифт. Шрифты грузятся из приложения (D33), запасной адрес CSP блокирует, а ловушка в e2e его пропускает; `csp.spec.ts` отдельно проверяет, что шрифт Excalidraw загружен.

## D38. Privacy и удаление аккаунта

**Цель.** Google требует ссылку на privacy policy для OAuth-приложения в режиме In production; пользователь должен уметь удалить свои данные.

| Вариант | За | Против |
|---|---|---|
| **Статическая страница `/privacy` (ссылка в футере главной); на ней же кнопка «Delete account» для вошедшего (меню аккаунта зафиксировано AT-43) → edge function `delete-account`: ключ из Vault, затем `auth.admin` удаляет пользователя, остальное уходит каскадом** — выбран | Удаление полное и атомарное по смыслу: секрет Vault не связан внешним ключом, поэтому удаляется явно первым | Ещё одна функция |
| Удаление по письму владельцу | Без кода | Не масштабируется, нарушает ожидания пользователей |
