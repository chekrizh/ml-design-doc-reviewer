# Чеклист перед автономным прогоном

Что должно быть готово до того, как оставить агента на несколько часов строить MVP.

Продукт: ML System Design Trainer (см. `docs/vision.md`). Две особенности: визуальный канвас требует браузерных e2e-тестов, а качество AI-помощника не проверить простым `assert`. Поэтому им посвящены пп. 4 и 5.

Пункты 1, 2 и эталонную разметку из п. 5 делает человек, агенту их поручать нельзя. Остальное можно подготовить вместе с агентом.

## 1. Продукт и объём MVP

- [x] Одно предложение о цели MVP: какой минимальный сценарий пользователь проходит от начала до конца (задача → канвас → решения → документ).
- [x] Явный список того, что НЕ входит в MVP (аккаунты, совместная работа, экспорт в разные форматы, большая база документов и т. п.).
- [x] Модель данных: задача, блок/компонент, решение (цель, альтернативы, плюсы и минусы, выбор), связи между блоками, итоговый документ.
- [x] Роль AI-помощника в проверяемом виде: по кнопке проверяет дизайн скиллом `ml-system-design-review` в чистом виде, включая «Fix»; находки привязаны к полям, без gradecard. См. `docs/mvp-spec.md` (M2) и D19.

## 2. Технические решения (их принимает человек, не агент)

- [x] Стек фронтенда (канвас) и бэкенда, менеджеры пакетов.
- [x] LLM-провайдер и модель, способ передачи ключа: OpenRouter, BYOK, модель выбирает пользователь, ключ в Supabase Vault (D16, D20).
- [x] Структура репозитория на верхнем уровне.
- [x] Список разрешённых зависимостей или правило «новую зависимость только с обоснованием в `docs/decisions.md`».

## 3. Список фич с критериями готовности

- [x] Файл `features.json`: 20–60 маленьких пунктов, у каждого описание, шаги проверки и `passes: false`.
- [x] Порядок пунктов: сначала каркас, потом ядро, потом «приятности».
- [x] Правило для агента: менять только поле `passes`, пункты не удалять и не переписывать.

## 4. Автоматическая проверка

- [x] Команды `test`, `lint` и `typecheck` запускаются одной строкой (Makefile или `init.sh`).
- [x] Детерминированные тесты без реального LLM: мок-клиент с записанными ответами (D14).
- [x] Браузерные e2e-тесты (Playwright): открыть задачу, добавить блоки, зафиксировать решение, получить документ.
- [x] Скриншоты ключевых экранов, чтобы агент мог визуально проверять канвас.

- [x] Приёмочные сценарии, написанные человеком: `docs/acceptance-tests.md`. Агент реализует их как тесты, но не меняет.

## 5. Оценка качества AI-помощника

- [ ] База реальных system design документов для помощника (стартовый набор, источник, формат). → M3, grounding.
- [x] Eval качества проверки в M2 не нужен: скилл оттестирован отдельно и не меняется. Наш слой (structured output, привязка находок к полям) проверяется обычными тестами на мок-клиенте. Eval-набор с эталонной разметкой вернётся вместе со скорингом и grounding в M3.

## 6. Память и навигация для агента

- [x] `CLAUDE.md`: стек, команды, конвенции, запреты, ссылки на спецификацию и `features.json`.
- [x] `progress.md`: по каждой фиче агент отмечает, какие критерии приёмки закрыл (ожидаем, что все).
- [x] `open-questions.md`: противоречия в spec и сценариях и расхождения с мокапами, которые агент не решает сам.
- [x] Правило коммитов: маленький коммит после каждого закрытого пункта, работа в отдельной ветке, не в `main`.
- [x] Инструкция на старт каждой сессии: прочитать progress и git log, запустить тесты, потом брать следующий пункт.

## 7. Окружение и права

- [x] Отдельная ветка или worktree, в идеале контейнер.
- [x] Настроены разрешения (auto mode или allowlist), чтобы агент не простаивал в ожидании подтверждений.
- [x] Явные запреты: `git push --force`, изменения вне репозитория, публикация чего-либо наружу.
- [x] Установлены и работают всё нужное для запуска: Node/Python, браузер для Playwright, Docker (если нужен).

## 8. Бюджет и стоп-условия

- [x] Лимит на реальные LLM-вызовы: в M2 прогон реальных вызовов не делает, только мок-клиент. Для M1: подписка, `autoContinueAtUsageLimit` включён в worktree.
- [x] Условия остановки: все фичи `passes` и eval выше порога, или N попыток подряд без прогресса на одном пункте. Во втором случае агент записывает проблему в progress и переходит к следующему пункту.
- [x] Способ оповещения, когда агент закончил или застрял (push-уведомление).

## 9. Приёмка после прогона

- [x] Заранее решить, что проверять руками:
  1. Прочитать итог в `progress.md` и всё в `open-questions.md`.
  2. `pnpm check` и `pnpm e2e` в worktree: убедиться самому, что всё зелёное.
  3. Пройти сценарий руками: пустой дизайн → свой system design на канвасе → документ → экспорт PDF и MD. Затем Load example.
  4. Сравнить экраны с `docs/mockups/`. Команды из раздела «Проверка» в `docs/design-system.md` дают пустой вывод.
  5. Проверить, что `docs/acceptance-tests.md` не изменён: `git diff docs/mvp-planning -- docs/acceptance-tests.md` пуст.
  6. Ревью ветки: `/code-review` на корректность и `ponytail-review` на лишний код.
  7. Решить: мёрж в `main`, доработка или повторный прогон.
